1 Executive Summary

ArchPlanner ist ein webbasiertes Analyse- und Planungswerkzeug für Unternehmensarchitektur, entwickelt von WAMOCON. Die Anwendung richtet sich an IT-Architekten, Projektleiter und technische Führungskräfte, die den Ist-Zustand ihrer Systemlandschaft strukturiert erfassen, KI-gestützt bewerten und einen konkreten Umsetzungsplan ableiten wollen.

Kernleistung der Anwendung ist ein fünfphasiger KI-Analyseprozess auf Basis von Google Gemini 2.0 Flash, der individuelle Risikobewertungen, Soll-Architekturempfehlungen und einen 5-Wellen-Umsetzungsplan generiert. Für den Betrieb ohne KI-API-Schlüssel steht ein vollständig lokal ausführbarer, regelbasierter Fallback bereit.

Die Datenpersistenz ist in zwei Modi ausgeführt: lokal via Zustand/localStorage (ohne Backend) und cloud-basiert via Appwrite (mit Authentifizierungspflicht). Jira-Integration erlaubt das direkte Anlegen von Vorgängen aus dem integrierten Aufgaben-Tracker. Analyseergebnisse sind als PDF und Word exportierbar.

Produktstatus

ArchPlanner befindet sich im produktiven Betrieb (Version 1.0.0). Alle Kernfunktionen sind implementiert und getestet. CI/CD via GitHub Actions ist aktiv; Testergebnisse und Coverage-Berichte werden automatisch auf GitHub Pages publiziert.

3 Benutzerhandbuch

3.1 Authentifizierung

Die Authentifizierung in ArchPlanner basiert auf Appwrite und ist für die Cloud-Persistenz von Projekten, Aufgaben und Konfigurationen erforderlich. Die Middleware erzwingt eine gültige Appwrite-Session bei jedem Seitenaufruf.

Anmeldeoptionen

MethodeFunktionsweiseVoraussetzung
E-Mail + PasswortDirektanmeldung mit gespeichertem Passwort via Appwrite createEmailPasswordSessionRegistriertes Konto
RegistrierungNeues Konto im Anmelde-Dialog anlegen; kein separates Portal nötigGültige E-Mail-Adresse + Passwort

Nach erfolgreicher Authentifizierung werden alle eigenen Projekte, Aufgaben, Snapshots, Chat-Verläufe und Konfigurationen aus der Appwrite-Datenbank geladen. Die Middleware leitet nicht authentifizierte Nutzerinnen und Nutzer automatisch auf /auth/login um.

3.2 Dashboard

Das Dashboard ist der zentrale Einstiegspunkt. Es zeigt eine Übersicht aller angelegten Projekte sowie aggregierte Kennzahlen.

KPI-KarteBedeutung
Projekte gesamtAnzahl aller gespeicherten Projekte
Ø Architektur-ScoreDurchschnittlicher Score aller Projekte (0–100); farblich codiert
Hohe RisikenGesamtzahl der als „hoch" bewerteten Risiken über alle Projekte

Klick auf eine Projektkarte öffnet die Detailansicht mit Analyseergebnis. Über den Button + Neues Projekt wird der Erfassungs-Wizard gestartet.

3.3 Projekt anlegen (4-Schritte-Wizard)

Der Wizard führt in vier Schritten durch die Erfassungsfelder. Fortgeschrittene Schritte werden durch Klick auf die Schrittnummern erreichbar, sobald sie abgeschlossen sind.

  1. Grundlagen — Projektname, Kundenname, Teamgröße, aktuelle App-Anzahl, geplante App-Anzahl (Ziel). Alle Felder unterstützen Freitexteingabe als „Andere..."-Option.
  2. Tech-Stack — Mehrfachauswahl von primärem Tech-Stack, Datenbanktechnologien, Hosting-Optionen sowie Erfassung von Legacy-Systemen (mit optionalem Freitext). Die Auswahl beeinflusst direkt die KI-Analyse und den Fallback.
  3. Prozesse — Code-Sharing-Strategie, Design-System-Reifegrad, CI/CD-Abdeckung, Testing-Abdeckung. Mehrfachauswahl mit vordefinierten Optionen.
  4. Infrastruktur — Monitoring-Abdeckung, Dokumentationsstand, Branching-Strategie, Onboarding-Dauer. Nach Abschluss dieses Schritts wird die Analyse gestartet.
Kein API-Key konfiguriert

Ist kein KI-API-Key in den Einstellungen hinterlegt, wird im letzten Schritt ein Hinweis angezeigt. Die Analyse wird regelbasiert durchgeführt. Ein API-Key kann jederzeit nachträglich in den Einstellungen ergänzt werden, die Analyse kann anschließend manuell neu gestartet werden.

3.5 Aufgaben-Tracker

Im Tab Aufgaben können Maßnahmen aus den Umsetzungswellen als Aufgaben angelegt und verwaltet werden.

StatusSymbolBedeutung

Klick auf das Status-Icon wechselt zyklisch den Status. Pro Aufgabe kann eine Notiz hinterlegt werden. Der Gesamtfortschritt über alle Aufgaben eines Projekts wird als Balken und Prozentzahl angezeigt. Aufgaben können mit einem Jira-Vorgang verknüpft werden (siehe 3.6).

3.6 Jira-Integration

ArchPlanner erlaubt die direkte Erzeugung von Jira-Vorgängen aus dem Aufgaben-Tracker. Mehrere Jira-Instanzen können gleichzeitig konfiguriert sein.

  • Konfiguration in Einstellungen → Jira-Verbindungen
  • Benötigte Angaben: Jira-URL, E-Mail, API-Token, Projektschlüssel, Vorgangstyp
  • Verbindungstest direkt in der Einstellungsseite
  • Beim Push kann aus allen konfigurierten Instanzen gewählt werden
  • Erstellter Vorgang wird mit Schlüssel und direktem Link in der Aufgabe gespeichert
Sicherheitshinweis

Jira API-Token werden in der Appwrite-Datenbank gespeichert. Die Verbindung erfolgt server-seitig über eine Next.js API-Route. API-Token werden nicht im Client-Speicher (localStorage) exponiert.

3.7 KI-Chat

Der KI-Chat ist ein projektspezifischer Dialogkanal. Die gesamte Analysestruktur (Risiken, Soll-Zustand, Wellen, Wizard-Daten) wird als Systemkontext an das KI-Modell übermittelt. Vorschlagsfragen erleichtern den Einstieg für neue Nutzerinnen und Nutzer.

Voraussetzungen

  • Aktiver KI-API-Key (Gemini oder OpenAI) in den Einstellungen konfiguriert
  • Chat-Verlauf wird projektbezogen persistiert (lokal oder Appwrite)
  • Chat-Verlauf kann pro Projekt gelöscht werden

3.8 Projektvergleich

Über die Sidebar-Navigation /compare können zwei Projekte aus dem eigenen Bestand gegenübergestellt werden. Angezeigt werden: Score, aggregierte Risikozählung (hoch/mittel/niedrig), Technologie-Kennzahlen sowie ein Tech-Stack-Differenzvergleich.

Voraussetzung: Mindestens zwei Projekte müssen im Dashboard vorhanden sein.

4.5 Datenpersistenz

ArchPlanner betreibt ein Dual-Persistenz-Modell: Die Zustand-Bibliothek mit persist-Middleware schreibt den Store-Zustand automatisch in localStorage. Parallel werden alle schreibenden Store-Aktionen an die Appwrite-Datenbankschicht weitergeleitet, sofern Appwrite konfiguriert ist.

BetriebsmodusPersistenzAuthentifizierung
Lokal (ohne Appwrite)localStorage via Zustand persistNicht erforderlich; Middleware leitet zu /auth/login um, sofern keine Appwrite-Session gesetzt
Cloud (mit Appwrite)Appwrite Database + localStorage (Fallback)Pflicht; Middleware erzwingt Redirect zu /auth/login

4.6 Authentifizierung

Die Authentifizierung basiert auf Appwrite (E-Mail / Passwort). Die Next.js-Middleware (src/middleware.ts) prüft bei jedem Request die Session via Appwrite-Session-Cookie (a_session_{projectId}) und leitet unauthentifizierte Anfragen an /auth/login um. API-Routen und statische Assets sind von der Umleitung ausgenommen.

Lokaler Betrieb mit Appwrite

Für lokalen Betrieb ist eine laufende Appwrite-Instanz erforderlich (Cloud oder Self-Hosted via Docker). Ohne gültige Appwrite-Session leitet die Middleware automatisch zu /auth/login um. Der Datenbankschicht (lib/appwrite/db.ts) ist ein Fallback-Nutzer local-dev-user hinterlegt, der greift, wenn keine Auth-Session verfügbar ist – jedoch erst nach Login.

4.8 Zugriffskontrolle

ArchPlanner verwendet anwendungsseitige Zugriffskontrolle: Alle Datenbankabfragen werden in lib/appwrite/db.ts mit Query.equal('user_id', userId) gefiltert. Jede Nutzerin und jeder Nutzer sieht und schreibt ausschließlich eigene Datensätze. Cross-User-Datenzugriff ist durch konsistente user_id-Filterung auf Abfrageebene verhindert.

5 KI-Analyse-Engine

5.1 Google Gemini 2.0 Flash

Die KI-Analyse nutzt gemini-2.0-flash als Modell. Der Analyseprozess ist in fünf sequenzielle Phasen aufgeteilt, die jeweils einen definierten JSON-Kontrakt zurückgeben:

PhaseInhaltOutput-Schema
Phase 1 / 5Zusammenfassung + die 2 kritischsten Kern-Risiken{ summary, risks[] }
Phase 2 / 5Erweiterte Risikoliste (bis 4 weitere Risiken){ risks[] }
Phase 3 / 5Soll-Zustand (Zielarchitektur-Empfehlungen){ soll[] }
Phase 4 / 55-Wellen-Umsetzungsplan{ waves[] }
Phase 5 / 5Score (0–100) und Score-Label{ score, scoreLabel }

API-Key-Auflösung

Der API-Key wird mit folgender Priorität aufgelöst: (1) Vom Client übermittelter Key aus der aktiven KI-Konfiguration, (2) Umgebungsvariable GOOGLE_AI_API_KEY. Fehlt beides, wird die Fallback-Analyse ausgeführt.

Rate-Limit-Behandlung

Bei HTTP 429 (Quota Exceeded) oder RESOURCE_EXHAUSTED-Fehlern parst die API-Route die Retry-After-Sekunde aus der Fehlermeldung und wartet entsprechend (+ 2 Sekunden Puffer). Maximal 5 Versuche pro Phase.

5.2 Regelbasierter Fallback

Die Fallback-Analyse (src/lib/fallback-analysis.ts) ist eine deterministische, vollständig lokale Engine ohne externe Abhängigkeiten. Sie leitet aus den Wizard-Daten skalierungssensitive Risikobewertungen und Empfehlungen ab.

Skalierungs-Logik

SkalierungsstufeKriterien
smallTeam ≤ 5, Ziel-Apps < 20
mediumTeam 5–15 oder Ziel-Apps 20–49
largeTeam 15–30 oder Ziel-Apps 50–99
enterpriseTeam > 30 oder Ziel-Apps ≥ 100

Auf Basis der Skalierungsstufe werden Risikoschweregrad, Risikobeschreibung und Handlungsempfehlung kontextuell angepasst. Erfasste Risikobereiche: Legacy-Systeme, Code-Sharing-Strategie, Testing-Abdeckung, Monitoring, CI/CD, Design-System, Branching, Dokumentation, Onboarding-Dauer.

5.3 Scoring-Modell

Score-BereichLabelFarbcodierung
71 – 100Gut / Sehr gutGrün

Der Score wird von der KI (Phase 5) auf Basis der gesamten Analyse generiert. Bei regelbasierter Analyse wird ein aus den Risikogewichtungen berechneter Score verwendet. Bei Neuanalyse wird der bisherige Score als Snapshot gespeichert.

6 Jira-Integration

Die Jira-Integration ist eine optionale Erweiterung des Aufgaben-Trackers. Sie ermöglicht das direkte Anlegen von Jira-Vorgängen aus ArchPlanner heraus, ohne den Bearbeitungskontext zu verlassen.

Technischer Ablauf

  1. Nutzer konfiguriert Jira-Verbindung in Einstellungen (URL, E-Mail, API-Token, Projektschlüssel, Vorgangstyp)
  2. Verbindungstest via POST /api/jira/test – prüft Authentifizierung und Projektexistenz
  3. Hover über Aufgabe im Tracker → Link-Icon sichtbar → Klick startet Vorgang-Erstellung
  4. Bei mehreren Jira-Konfigurationen: Instanz-Auswahl per Dropdown
  5. POST /api/jira/issue erzeugt den Vorgang in Jira via REST API
  6. Erstellter Vorgang: Schlüssel (z.B. PROJ-42) und direkter URL werden in der Aufgabe persistiert

7 Export-Funktionen

PDF-Export

Bibliothek: jsPDF + jspdf-autotable. Generierung vollständig client-seitig. Das erzeugte PDF enthält:

  • Deckblatt mit Projektname, Kundename und Analysedatum
  • Score-Anzeige mit Label
  • Zusammenfassung (KI-generiert oder regelbasiert)
  • Ist-Zustand als Übersichtstabelle
  • Vollständiger Risikokatalog nach Schweregrad
  • Soll-Zustand (falls vorhanden)
  • 5-Wellen-Umsetzungsplan
  • Aufgaben-Liste mit Status

Word-Export (DOCX)

Bibliothek: docx (v9). Generierung vollständig client-seitig. Erzeugt ein strukturiertes DOCX mit Überschriften, formatierten Tabellen und farbiger Risikokennzeichnung. Geeignet zur Weiterbearbeitung in Microsoft Word oder kompatiblen Programmen.

Client-seitige Generierung

Beide Export-Formate werden ohne Server-Roundtrip erzeugt. Analysedaten verlassen den Browser nicht erneut. Der Download startet direkt nach der Generierung.

npm run db:stop    # Datenbank stoppen
npm run db:reset   # Datenbank zurücksetzen (Daten löschen + Schema neu einspielen)
npm run db:logs    # Datenbankprotokoll streamen
